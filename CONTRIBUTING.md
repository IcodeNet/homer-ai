# Contributing

This page is for people who change the course itself. If you're here to learn, you want the [README](README.md). For how the code fits together, read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md); for why it is built this way, [docs/decisions/](docs/decisions/README.md).

## How do I change a notebook?

You don't, not directly. Every notebook and every chapter README is **generated**: the text lives in the `scripts/course/` package, and `scripts/build_notebooks.py` runs it. So you edit the content there, then rebuild.
Chapter N lives in `scripts/course/chNN_*.py` (for example chapter 5 is `ch05_training.py`, and the toolbox appendix is `appendix_a_toolbox.py`). The shared helpers are in `cells.py`, the shared code cells in `setup_code.py`, the diagrams in `diagrams.py`, and the chapter README facts in `readmes.py`. Then rebuild:

```
uv run python scripts/build_notebooks.py
```

If you change a notebook or chapter README directly, the next build simply overwrites it. So never hand-edit a `.ipynb`.
A blank starting point for a new notebook is [scripts/templates/00_template.ipynb](scripts/templates/00_template.ipynb) (also generated by the script).

## How do I check my change?

Run these from the project folder. CI runs the same checks ([.github/workflows/ci.yml](.github/workflows/ci.yml)), so it's nicer to catch problems here first.

```
uv run ruff check                       # find mistakes in the code
uv run ruff format --check              # check the layout (drop --check to fix it)
uv run pytest                           # tests of src/homer_ai, incl. the chapter 8 helpers, the chapter 9 search and the chapter 10 tools and data (under a minute, CPU only)
uv run python scripts/build_notebooks.py   # rebuild; run it twice: the second run must change nothing
uv run python scripts/run_notebooks.py     # run every notebook top to bottom in a real kernel
uv run python scripts/run_notebooks.py --solutions   # run the notebooks that have exercises, with the solutions filled in
uv run python scripts/check_links.py       # every relative link in READMEs and notebooks must point at a file
uv run python scripts/export_diagrams.py   # redraw docs/images/*.png; commit them if they changed
```

The tests use the ready-made `models/odyssey_book1.pt` (they set `HOMER_MODEL`) and never write a model file. The checkpoint tests write to a temporary folder.
To re-measure the numbers in the README table: `uv run python scripts/baselines.py`.

## How do I add a "Your turn" exercise?

With `exercise(...)` from `scripts/course/cells.py`, unpacked into the list of cells with a `*`. One call makes five cells: the task, a starter code cell, a check cell, a folded hint and a folded answer.

```
*exercise(
    "which numbers does `ἄνδρα` get?",                # the heading: ### ❓ Your turn: …
    "Encode it with Book 1's real tokenizer.",         # the task
    starter="# 👉 do: turn the word into its list of IDs\nandra_ids = None",
    solution='andra_ids = tokenizer.encode("ἄνδρα")',
    check='check("the IDs of ἄνδρα", andra_ids, [58, 38, 29, 42, 26], coach="…")',
    hint="The cell above did it for `μοῦσα`.",
    answer="`ἄ` is 58 and plain `α` is 26: two different characters.",
),
```

- Keep it small: one to three lines to write, on variables the notebook already has. Give the blanks names no later cell uses.
- Every blank in the starter is `None`, so the cell runs as it is. The solution is the whole starter cell, filled in.
- `check` (in `src/homer_ai/lessons.py`) compares the answer with the right one and prints ⏳, ✅ or ❌. It never raises. For an answer with more than one right value, pass `test=` and `expected=`; `show=` makes the values readable in the message.

`scripts/run_notebooks.py` checks the exercises both ways, and CI runs both. A normal run leaves the blanks as `None`, and every check must print ⏳. With `--solutions`, each starter cell is replaced (in memory) by the code from its folded answer, and every check must print ✅. The script finds the cells by the tags that `exercise()` sets: `exercise-starter`, `exercise-check` and `exercise-solution`. So a solution that stops working fails CI.

## What about the notebooks that download something big?

Chapter 8 fine-tunes GPT-2, so notebooks 08_01 to 08_04 download its weights once (548 MB, to `~/.cache/homer-ai/`, or to the folder named by `HOMER_CACHE`) and then train for a minute or two each. Notebook 10_02 uses the same file. On your own computer, `scripts/run_notebooks.py` runs them like any other notebook. CI doesn't download the file. It sets `HOMER_SKIP_DOWNLOADS=1`:

```
HOMER_SKIP_DOWNLOADS=1 uv run python scripts/run_notebooks.py
```

With that set, the notebooks listed in `NEEDS_DOWNLOAD` in `scripts/run_notebooks.py` aren't run. They're still read and checked for a valid notebook format, and shown as `skipped`. So if you change chapter 8 or 10_02, run those notebooks yourself before you push. A new notebook that needs a big download goes into that list.

The chapter's helper code (`pretrained.py`, `finetune.py`, `lora.py`) lives in `src/homer_ai/` with the rest of the code. Its tests are in `tests/test_fine_tuning.py`; they build tiny stand-in files in a temporary folder and never download. Fine-tuned models are never committed: anything the chapter saves goes to the cache folder.

## What do I check when I change the search of chapter 9?

The search (`src/homer_ai/retrieval.py`) is scored on the 40 labelled questions in [data/eval/](data/eval/README.md). `tests/test_retrieval.py` pins those scores, so a change to the tokenizer, to BM25 or to the questions makes a test fail until you update the numbers there and in the tables of `scripts/course/ch09_grounded_answers.py` and [ADR 0006](docs/decisions/0006-bm25-from-scratch-for-search.md).
If you add a question, look its answer up in `data/homer/<poem>/english/` and write down the book and lines from the file.

Two things in the chapter aren't run by CI. The comparison cell in 09_02 needs the optional extra (`uv sync --extra rag`) and a model download; without the extra it prints one line.
And `scripts/benchmark_grounding.py` calls Claude through the Claude Code command line, so it uses your account. Notebook 09_04 shows one recorded run with its date, model and command; if you run it again, update that table.

## What do I check when I change chapter 10 or its data?

Everything in [data/domain/](data/domain/README.md) is invented, and it has to stay that way: no real company, product, person or customer text, and nothing copied from a real firm's documents ([ADR 0007](docs/decisions/0007-synthetic-data-for-the-domain-chapter.md)).
The emails and tickets are generated. To change them, edit the sentence lists in `scripts/make_domain_data.py` and run it; never edit the two `.jsonl` files by hand:

```
uv run python scripts/make_domain_data.py           # writes emails.jsonl and tickets.jsonl
uv run python scripts/make_domain_data.py --check   # exits 1 if the committed files differ
```

`tests/test_domain.py` pins the numbers that need no model (the support search, the guard, the keyword baseline, the article suggestions, the three routers), so a change to the data or to `src/homer_ai/domain.py` makes a test fail until you update the numbers there and in the tables of `scripts/course/ch10_your_domain.py`, [ADR 0007](docs/decisions/0007-synthetic-data-for-the-domain-chapter.md) and the data README.
The numbers of the fine-tuned model in 10_02 (and of the optional cell in 10_03) come from running the notebook: run it and update the *What you saw* tables.

`scripts/benchmark_domain.py` calls Claude through the Claude Code command line, with the chapter's MCP server connected, so it uses your account and CI never runs it. Notebook 10_01 shows one recorded run with its date, model and command; if you run it again, update that table.
To try the server by hand: `uv run python -m homer_ai.domain_server` (it waits for an MCP client on stdin; Ctrl+C stops it).

## What are the diagram images in `docs/images/`?

GitHub shows notebooks without their output, so the course's main diagrams are also saved as PNG files. The README and the chapter READMEs show them.
`scripts/export_diagrams.py` draws them from the `DIAGRAM_*` code in `scripts/course/diagrams.py` (the same code the notebooks run), with a fixed font and no metadata, so re-running gives identical files.
To change one, edit it in `diagrams.py`, rebuild, run the export and commit the new PNGs. CI runs `uv run python scripts/export_diagrams.py --check`, which draws the diagrams again and fails if one is missing or looks different (it allows the tiny pixel differences you get between macOS and Linux).
To show a new diagram, add a line to `DIAGRAMS` in `scripts/export_diagrams.py` (file name, which `DIAGRAM_*` constant, the inputs it needs, the notebook, and the alt text); the chapter README picks it up.

## What is the pre-commit hook?

It's optional. `.pre-commit-config.yaml` runs Ruff and rebuilds the notebooks before each commit, and stops the commit if a notebook changed, which means you forgot to rebuild.
To use it: `uv tool install pre-commit`, then `pre-commit install`.

Notebook headings use the course number that matches the file name (`02_02 Special tokens`). The book section goes only in the `📖 Book:` tag under the heading.

## What do the commands `homer-train` and `homer-serve` do?

`uv run homer-train --model gpt` trains the GPT of chapter 4 (about 3 minutes) and writes `src/homer_ai/homer_gpt.pt`.
`uv run homer-train` (default `--model char`) trains the small one-head model (about 8 minutes) and writes `src/homer_ai/homer_model.pt`.
`uv run homer-serve` starts the MCP server over stdio, with its two tools (`consult_homer_llm` and `search_homer`). It picks its model from `$HOMER_MODEL`, else your own `homer_gpt.pt`, else `models/odyssey_book1_gpt.pt`, else your own `homer_model.pt`, else `models/odyssey_book1.pt`, and logs each call to stderr.

## What are the style rules?

- Every sub-heading is a learner question (`### ❓ …`), answered in plain English. Say each thing once.
- Write the way you'd talk a friend through it: "we" and "you", short sentences, plain words. No buzzwords, no em dashes, and bold only for the one thing that matters in a paragraph.
- Start from a tiny real piece of Homer, show it as an aligned picture, ask the learner to predict, then run code that prints the same picture.
- Explain every technical term the first time. The reader is a developer new to ML: explain ML, maths and PyTorch, not general programming.
- Graphs use `src/homer_ai/studio_style.py`; never hard-code colours.
- In an exercise's starter cell, `# 👉 do:` says what to write and `# 💡 hint:` gives a nudge. The `coach=` line of a check names the likely mistake and where to look ("Got 0.7? Then you added the mistake."), and never just says "wrong".
- The recap has at most 3 points. After them, `can=[...]` adds a "You can now" list of 2 to 4 skills, each starting with a verb.

## How is the Greek and English text made?

`scripts/corpus/` downloads and builds `data/homer/` (`download.py`, `build.py`), and `check.py` checks it. See [data/homer/README.md](data/homer/README.md) for sources and [data/homer/LICENSE.md](data/homer/LICENSE.md) for licences (the MIT licence does not cover `data/homer/`).

## How do I change a ready-made model?

First, never overwrite `src/homer_ai/homer_model.pt` or `homer_gpt.pt` from a notebook. See [models/README.md](models/README.md) for how the shipped models were made and how to reproduce them.
